# FS-06 · Per-row queries and unbounded fetches invisible at seed scale

List, bulk and tree code issues a query per row (SerializerMethodField .count()/.values_list() bypassing prefetch, per-item loops inside 'bulk' endpoints, recursive per-node aggregates, per-entity external API calls), multiplies joins (sibling Count(distinct)), or fetches whole collections unpaginated. Seed data has about ten rows, so it passes review and tests until real tenants load it.

**Triggers**
- a serializer gains a SerializerMethodField or helper that touches a related manager
- a new bulk endpoint loops an existing per-item helper; save()/create() inside a for-loop
- a queryset annotates two or more Count() over different reverse relations
- tree/hierarchy aggregate, per-status count loop, or per-user external API call on a page
- a new UI panel calls a list endpoint without page_size, or a response serializes the same rows twice
- an org-wide scan, drift detector or batch loop over prod-scale tables (subprocess per item, __contains on an unindexed column, a full report builder called for one scalar)

**Guards**
- Write a query-count test at two sizes (N=1 vs N=10) asserting it stays flat before implementing
- Resolve per-row data via annotate/prefetch and iterate prefetched .all(); never .values_list() in a hot serializer path
- Replace per-item loops with pk__in batch fetches, bulk_create and one GROUP BY; use Subquery instead of sibling Count(distinct)
- Default new list consumers to paginated fetches, check the largest real tenant's row count, and measure real per-request latency, not only query count
- EXPLAIN new filters on large tables, write detectors as one set-based query, and loop batch work inside one warm process
