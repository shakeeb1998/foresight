# FS-113 · Capacity, concurrency or quota set without the platform's resource math

Memory, vCPU, executor counts, thread pools, parallel transfers and task counts are tuned from a hypothesis or copied numbers without checking the platform's fixed limits (EMR Serverless memory/vCPU ratios, Batch CE overhead, account quotas), the host's size, per-host S3 limits, connection-pool sizes or shared quotas like a vendor thread pool. Jobs OOM, get throttled, or exceed a quota that the test account still had room for.

**Triggers**
- changing cpu/memory/executor/initialCapacity settings for EMR Serverless, EMR or Batch
- copying parallelism defaults from a bigger machine or a daily job to a backfill
- a thread pool around a boto3 client, or scaling tasks that share a capped external pool
- adding a quota-capped AWS resource (on-demand Kinesis stream, Batch CE) in prod

**Guards**
- Read the Pulumi worker size and the service's documented limits before editing Spark conf; fit conf to infra, not infra to guesses
- Compute concurrency x per-unit memory against the instance; leave agent/OS overhead on Batch
- Match boto3 max_pool_connections to thread count; model shared quotas (vendor thread pools) from measured peak, not stated baseline
- Check current account quota usage in prod before adding capped resources
- Size backfill windows from per-run shuffle volume, not calendar units
