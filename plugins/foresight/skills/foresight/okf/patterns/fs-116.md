# FS-116 · IAM policy written from SDK names or memory instead of the client's actual API calls

Policies are drafted from SDK method names, guessed condition attribute names, or 'least privilege' intuition: tools like rsync need list/read on the destination, ListBucket is evaluated on the bucket resource with s3:prefix including parent prefixes, condition keys apply only to some actions, managed services read with their own service agent, new principals need propagation time. A missing grant gets 'fixed' with a wildcard.

**Triggers**
- writing a least-privilege policy for a CLI/tool or managed service
- an action name copied from an SDK method (HeadObject, ListObjectsV2)
- a prefix-scoped condition or a CEL/condition key typed from memory
- AccessDenied on one resource in an allow-list policy

**Guards**
- Look up each action and condition key in the service authorization reference
- Enumerate the API calls the tool makes (CloudTrail, --debug) and grant exactly those
- Add the missing resource rather than a wildcard; include parent prefixes in s3:prefix conditions
- Grant managed-service agents explicitly and wait for/verify principal propagation
