# FS-85 · Status-gated behavior written for the states in view, not every value of the enum

UI and backend behavior keyed on a record's status (an action gate, a disabled button and the chip that explains it, a label map, the transition an action calls) is written and tested for the one or two states in the current design frame or ticket. Other values of the same enum fall through: a shared gate narrowed to one origin case hides Sign/Accept for another and deadlocks the flow, a button shown in several states calls a transition the backend table rejects from some of them (409), a disabled control has no status chip for the state that disables it, and a label map borrowed from another surface makes a pending state read as confirmed. Only the covered branch has e2e coverage, so users hit the rest in production.

**Triggers**
- adding or narrowing a condition on a status/source enum inside a shared action-gate boolean during a UI or pixel-match pass
- one UI action/button rendered in more than one record state but routed to a single transition endpoint
- a control's enabled/disabled state depends on an enum while the chip/badge mapping was written earlier for fewer values
- reusing an existing enum-to-label map from another page for a new design that specifies its own vocabulary
- a shared failure/retry component reused for a second action but exposing a single retry callback

**Guards**
- List every value of the enum and write a state x action matrix (visible, enabled, which transition) before editing a gate; add one test per branch
- For each state where the FE shows an action, check that the backend transition table allows the exact resulting transition and add an API test per state
- Confirm every status that disables a control has a visible indicator explaining it
- Diff each enum-to-label map against the design's vocabulary and assert the literal label text for every status in e2e
- Test per failure kind that retry invokes the matching action
