# FS-124 · Parallel lanes create test DBs, pools or ports named per lane, and nobody owns teardown

A fan-out gives each lane its own e2e pool, worker databases, template DB or ports, named from the lane label. N lanes then mean up to 3N databases, and the "drop these when done" step is a printed hint that nobody runs. One 24-lane run left 9 idle pool DBs, an earlier wave left hundreds of per-worker test DBs, and dead lanes kept pool reservations that held a live lane at the admission gate for 40 minutes.

**Triggers**
- about to dispatch 2 or more lanes that each run e2e, pytest or a server and each wants its own DB, ports or cache
- a run script exports a DB or port name built from the lane label
- a lane ends (merged, parked or dead) and its DBs, pool slot, ports or output folders are still there
- the database count is far above live lanes x workers
- a cleanup or sweep tool is about to be tested or run against the real database

**Guards**
- Name shared test resources by a bounded, reusable key (pool slot, worker index), never by lane label, so the count is capped by slots x workers and not by lane count
- The tool that creates a resource owns its teardown: the lane end hook drops the slot's DBs itself and skips only a DB with an open connection; a printed hint does not count
- Sweep orphans at the end of every wave and before the final report: pool-style DBs that no live slot holds, with zero connections, protected names excluded; report the DB count before and after
- Test teardown with a fake psql, and make the test environment unable to reach the real database (an env override set for every test), because a cleanup tool tested against the live DB drops live data
- Before reporting a run done, list databases, worktrees, pool state and listening ports and attach the delta to the report
