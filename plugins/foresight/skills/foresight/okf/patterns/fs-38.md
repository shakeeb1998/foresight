# FS-38 · Soft-deleted and terminal-state rows ignored by constraints and queries

Rows in deleted, archived or rejected states still participate in unique constraints, joins and aggregates, or their dependents are not cascaded: re-create after soft delete 500s on the unique constraint, Count() through relations bypasses the soft-delete manager, dedupe keeps a phantom row, SET_NULL parents un-hide children, deleting a bot leaves its membership seat, cascade restore via all_objects conflates batches.

**Triggers**
- the model uses SoftDeleteModel and has a unique/unique_together constraint or natural key
- an aggregate, annotation or join reaches a soft-deletable model
- deleting an entity that owns related rows (membership, synthetic user, children)
- a constraint meant as 'one active X' written as 'one X ever'
- a get-or-restore or create path that revives a soft-deleted row a merge deliberately removed; callbacks that can write to a terminal-state task
- a serializer inlines a Prefetch of a soft-deletable model in a payload that an offline-sync pull persists to devices
- re-entering work through a chat/run thread whose session already completed

**Guards**
- Test soft-delete then re-create with the same key; look up all_objects by natural key and revive before create
- Add filter=Q(is_deleted=False) to aggregates and compare list vs detail counts
- Use conditional unique constraints scoped to active status; cascade soft-delete to children with a batch id
- Test deleting the parent and assert dependent rows/seats are released
- Check the merge log and deletion reason before reviving; reject writes to terminal states
- Filter deleted_at in every Prefetch/inline queryset of a soft-deletable model and add a sync test that a soft-deleted child disappears on the other device
- Treat completed sessions as terminal: re-entry starts a new round, never resumes a finished one
