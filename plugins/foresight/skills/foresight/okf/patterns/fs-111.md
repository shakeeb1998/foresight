# FS-111 · Data type, unit, layout or source assumed from a name or sample instead of read from the producer

Queries, schemas, joins and DQ checks are written from a column's name, a pasted sample, a test fixture, a TS interface or a couple of sampled files: string dates treated as DATE, epoch unit guessed, partition layout asserted, a Glue/Spark schema typed from field names, a similar column taken from the wrong table, uniqueness or absence-as-NULL assumed. Code runs and returns plausible numbers, so the mismatch shows only when a user checks real rows.

**Triggers**
- writing SQL/PySpark against a table or column not yet inspected in this session
- a type, unit or format inferred from a field name (user_id, created_at, *_code) or a single pasted value
- hand-writing a Glue/StructType/DDL schema for a vendor payload or from a design doc
- two tables expose a similarly named column, or a dedup is removed because a table is 'already unique'
- a backfill over months of files whose encoding was checked on one or two samples
- claims about what an API returns derived from type definitions or mapper code

**Guards**
- Read the producer first: Glue schema (get-table), the writer's partition_keys/MERGE key, or the mapper that emits the field
- Sample real rows (DISTINCT, min/max, typeof, count by format) across the full date range before fixing a type, unit, grain or encoding boundary
- Check join-key uniqueness with GROUP BY key HAVING count(*)>1 before joining or dropping a dedup
- Validate a hand-written schema against one real payload/parquet file per time slice
- State the source table and column for every metric before computing it
