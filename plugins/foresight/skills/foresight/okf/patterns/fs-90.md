# FS-90 · Repo tooling bound to one machine's interpreter or to an unprovisioned worktree

Git hooks and test entry points hardcode an absolute interpreter path (a python.org framework build) or assume `python` is on PATH, and new worktrees ship without a venv. On another machine or worktree the hook can't start, or runs an interpreter that lacks native wheels and blocks by design. Each session then rediscovers which Python has pytest and the parsers, installs them by hand, and pushes with --no-verify.

**Triggers**
- a committed git hook or script references an absolute interpreter path (/Library/Frameworks/Python.framework/..., /opt/homebrew/bin/python3.x)
- the first git push from this machine or worktree in the session
- starting work in a fresh .claude/worktrees/* checkout with no .venv and no `python` on PATH, on a host with several system Pythons
- the hook needs native extension wheels (tree_sitter parsers) that only one installed interpreter has
- bot lanes or hooks running repo commands under the host's default node/python instead of the repo pin; a fresh per-lane DB used by the test command

**Guards**
- Make hooks resolve the interpreter in order (repo .venv, then PATH python3) and check required imports up front with a clear message instead of a silent block
- Ship one bootstrap command (make venv / scripts/setup) that builds the pinned-version venv with requirements plus test deps, and run it as step 0 in every new worktree
- Before any documented --no-verify escape, run the exact gate the hook would run with the working venv and paste its green result into the PR body
- After the second bypass, fix the hook on main instead of bypassing it again (FS-53)
- Pin the runtime per repo (.nvmrc, .python-version) in every lane env and hook, and make the lane test command provision its DB (migrate deploy) first
