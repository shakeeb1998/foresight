# FS-14 · Failure cause attributed without a controlled comparison

A failure is blamed on, or cleared from, the current diff, or a root cause is declared, without evidence that isolates it: no baseline run on a pristine base, truncated output read as absence, correlation instead of tracing the render path, host contention read as a regression, prod 500s with no traceback because logging isn't configured. Time is burned, or a wrong fix or claim ships.

**Triggers**
- failures in files/specs the diff never touched, or right after a rebase/merge
- about to say 'pre-existing', 'baseline' or 'root cause confirmed'
- diagnosing from head/tail snippets, status codes, or timings on a shared machine
- a prod/staging 500 or outage with no traceback or alert available
- a new imbalance or residual pattern-matches a previously seen anomaly class; several subagents agree on a diagnosis
- about to write a subagent's or a workaround's causal claim ('platform X can't do Y', 'the branch lacks Z') into memory or a skill; a bug report names a specific screen/flow while exploration found a similar-looking bug elsewhere
- every CI job on a self-hosted host slows by a similar percentage after a network change, with no related code change

**Guards**
- Run the identical failing set on a clean origin/<base> worktree and diff failing-test sets before attributing either way
- Quote the actual traceback/log line when declaring a root cause; without one, call it a hypothesis and add logging/health checks
- Grep full output instead of truncating; repeat timing measurements and check load average
- Check memory for known baseline-red suites and fix them at repo level instead of re-proving them each session
- Attribute the exact residual to specific ledger rows and read the posting function before naming the class; treat subagent consensus as shared anchoring, not independent evidence
- Verify a causal claim against the actual branch/device before persisting it, or label it an untested hypothesis; reproduce the user's exact reported flow before fixing a look-alike
- Check host-level causes first when degradation is uniform: time raw DNS lookups (dig, getent hosts) and read /etc/resolv.conf before app-level theories (sharding, pools)
